# RMT-86 — Неверный порядок элементов со статусами в чек-листе

**Тип:** Functional / Requirements-based testing  
**Проект:** «ПО Ремонт» Android MVP  
**Платформа:** Android, физическое устройство  
**Severity:** Minor  
**Priority:** Medium

## Контекст

В требованиях к экрану «Чек-лист проверки этапа» задан порядок отображения блоков в зависимости от статуса:

1. Не проверенные
2. С дефектами
3. Пропущенные
4. «Все хорошо»

Проверка проводилась сравнением реализованного поведения с документацией проекта.

## Предусловия

- приложение «ПО Ремонт» запущено;
- создан или открыт проект ремонта;
- выбрано помещение и этап;
- открыт экран «Чек-лист проверки»;
- в списке есть блоки с разными статусами.

## Шаги воспроизведения

1. Открыть чек-лист проверки этапа.
2. Установить или использовать блоки с несколькими статусами: «Не проверен», «Все хорошо», «Пропущен», «Дефект».
3. Просмотреть порядок элементов в списке.
4. Сравнить его с порядком, указанным в требованиях.

## Фактический результат

На проверенном экране элементы отображались в порядке:

1. Не проверен
2. Все хорошо
3. Пропущено
4. Дефект

Таким образом, блок с дефектом оказался ниже успешно завершённого и пропущенного блоков.

## Ожидаемый результат

Элементы должны группироваться в соответствии с документацией:

1. Не проверенные
2. С дефектами
3. Пропущенные
4. «Все хорошо»

Исправленные дефекты согласно требованиям должны отображаться в конце группы дефектов.

## Почему это важно

Порядок задан в требованиях не случайно: активные дефекты должны оставаться заметнее успешно завершённых проверок. При длинном чек-листе нарушение сортировки потенциально усложняет пользователю поиск проблемных пунктов.

## Что было сделано QA

- найдено расхождение между фактическим поведением и требованиями;
- проверен сценарий с несколькими статусами одновременно;
- зафиксированы actual и expected result;
- приложено визуальное подтверждение;
- дефект передан на исправление.
