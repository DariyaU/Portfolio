# API testing — что я могу объяснить на собеседовании

Этот файл помогает подготовить устное объяснение учебной практики. Он не заменяет коммерческий опыт.

## 1. Что я делала в Postman?

> В рамках обучения работала с REST API в Postman. Использовала GET, POST, PUT и DELETE, передавала path и query parameters, JSON request body, headers и переменные. Разбирала позитивные и негативные сценарии, а также готовые Postman scripts и проверки ответа. В портфолио сохранила коллекции User, Petstore и Swagger Petstore.

## 2. Чем path parameter отличается от query parameter?

> Path parameter является частью пути к ресурсу, например `/pet/{petId}`. Query parameter передаётся после `?`, например `/pet/findByStatus?status=available`. В тестировании проверяю корректные, некорректные и пограничные значения параметров.

## 3. Что проверяешь после отправки запроса?

> В первую очередь HTTP status code. Затем response body: JSON-структуру, наличие обязательных полей и корректность ключевых значений. При необходимости проверяю headers, Content-Type и формат ошибки.

## 4. Что проверяешь в POST/PUT?

> Метод, endpoint, headers, JSON body, обязательные поля и типы данных. После ответа проверяю status code и response body. Для изменения ресурса дополнительно проверяю, что новое состояние действительно соответствует ожидаемому.

## 5. Какие негативные проверки можешь привести?

> Невалидный статус или другой параметр, отсутствующий обязательный параметр, некорректный ID, пустое значение, неполный или некорректный JSON body. Для каждого сценария ожидаю корректную обработку ошибки и соответствующий HTTP-код согласно контракту.

## 6. Что такое CRUD?

> Create — POST, Read — GET, Update — PUT, Delete — DELETE. При тестировании CRUD важно проверять не только отдельные ответы, но и состояние ресурса после операции.

## 7. Зачем нужны переменные в Postman?

> Они позволяют не дублировать значения и менять окружение или идентификаторы без редактирования каждого запроса. В учебной коллекции использовались, например, `base_URL` и `pet_ID`.

## 8. Что такое Postman scripts?

> Это JavaScript-код, который можно использовать до отправки запроса или после ответа. В учебных коллекциях есть scripts/tests. Я могу объяснить их назначение и принцип проверки ответа, но не буду выдавать учебную практику за коммерческую автоматизацию API.

## 9. Как связать API и тест-дизайн?

> Для API применяю те же принципы тест-дизайна: позитивные и негативные сценарии, классы эквивалентности, граничные значения, проверки обязательных полей и некорректных типов. Для enum-параметров отдельно проверяю допустимые и недопустимые значения.

## 10. Что честно сказать про уровень?

> API-тестирование у меня сейчас учебное. Коммерческий опыт у меня связан прежде всего с тестированием корпоративного ПО: функциональные, smoke, regression, integration, exploratory и black-box проверки, работа с дефектами, установками и обновлениями. Postman и REST API я использую как дополнительную компетенцию и развиваю её для перехода в QA Engineer.

## Что не нужно говорить

- «У меня коммерческий опыт API-тестирования» — это не подтверждено.
- «Я автоматизировала API-тесты» — если речь только о готовых учебных scripts, так говорить нельзя.
- «Я уверенно работаю с SQL/Git как в коммерческом проекте» — это не подтверждено текущим опытом.
- «Я полностью Middle по API» — портфолио этого не доказывает.
